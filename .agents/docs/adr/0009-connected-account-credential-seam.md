# Connected Account Credential Seam

Better Agent will store the credential that backs a **Connected Account** as a mirror of the existing MCP catalog/connection pattern, and a **Thinkspace Agent** will read that credential only at tool-execution time, after the action's **Approval** is granted. A `connected_account_catalog` of available providers (seeded with GitHub) and a per-user `user_connected_accounts` table holding an encrypted credential sit beside the MCP server catalog and connection; a `connected_account_credential` **Permission** sits beside `mcp_tool_access`; and the potency rule gains a Connected Account branch beside its MCP one. A Connected Account is a product-level relationship — one per provider per user, reused across Thinkspaces — and the encrypted credential merely backs it; the relationship is never the credential string. A connected-account tool is offered to the agent only when it is enabled on the active **Agent Profile** revision, the Thinkspace holds the Permission, **and** a backing credential actually exists (enablement ∩ Permission ∩ credential — fail closed), and the credential is decrypted and used only inside the held tool's `execute`, which runs only after the owner approves the specific action.

We are choosing this over a bespoke credential store, and over reading the credential at proposal/hold time, because the MCP pattern already proved the catalog / connection / Permission / potency shape on this stack (ADR-0002, ADR-0004), and because deferring credential use until after Approval turns ADR-0003's holdpoint into a hard security boundary rather than a UI convention: the act of consenting is what unlocks the credential, so the worst a rejected proposal can do is nothing. The agent never receives the credential in its context — only the tool's post-Approval execution does — and a failed external call (an expired or revoked credential, or any provider error) surfaces as an honest tool failure the agent reports truthfully plus a prompt to reconnect, never a fabricated success (extending the grounding posture of PR #106). The consequence is that connecting and using an external account costs more setup and an explicit per-action Approval, in exchange for a credential that is encrypted at rest, bounded by both the provider's own grant and the user's Approval, and structurally untouchable by any action the user did not consent to.

The first provider is GitHub via a fine-grained Personal Access Token the user pastes and the product validates — resolving and storing the account identity at connect time — while full OAuth is deferred, with the connection's expiry and refresh-token columns reserved so it lands as an additive change rather than a migration. Considered alternatives: reusing the model-provider credential table (rejected — it is typed to model BYOK, and a Connected Account is a distinct catalog per ADR-0004); a general connected-account tool adapter with pluggable credential providers and OpenAPI ingestion (deferred — over-built for one provider and one tool); and enforcing a per-Thinkspace repository allowlist now (deferred — redundant with the per-action Approval until standing approval policies exist, ADR-0003). The standing constraint, reinforcing ADR-0006, is that this is Better Agent's own credential seam: Think's MCP and OAuth machinery are implementation tools, while the Connected Account, its Permission, and the Approval remain the authoritative product concepts.
