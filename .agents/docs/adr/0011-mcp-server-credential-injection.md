# MCP Server Credential Injection

Better Agent will let a **Thinkspace** be granted and run an authenticated MCP server by injecting its credential as transport headers when the **Thinkspace Agent** connects the server for a turn. An authenticated MCP server (`authType` of `bearer` or `api_key_header`) is grantable exactly like an auth-free one — the grant records the capability on one axis while the credential lives on another — and the credential is resolved only inside the Durable Object's per-turn `addMcpServer` call, never written to the transcript, surfaced to the model, or logged. Two credential sources back it: a **registered connection** carries its own per-user encrypted headers (the existing `user_mcp_connections.encrypted_headers`, decrypted at connect time with the worker's encryption secret), and a **built-in authed server** — only `context7` today — reads a product-level secret from the worker env (`CONTEXT7_API_KEY`), since built-ins have no per-user secret store. The potency rule gains an MCP arm of the credential-exists axis beside its Connected Account one: a granted authed server is potent only while a credential resolves (registered headers present, or a configured product key), so clearing a connection's headers or leaving a product key unset flips the tool inert — and the runtime fails closed at connect if a credential is somehow absent at use.

We are choosing transport-time injection over the connected-account pattern of reading the credential inside a held tool's `execute` (ADR-0009) because an MCP credential authenticates the whole *server connection*, not a single action: the agent cannot list or call any tool on the server until the connection is established, so the credential must be present at connect, before any tool runs. This differs from a connected-account mutation, where the credential gates one consented action and consent is what unlocks it. The safety posture is preserved by composition rather than by deferring the credential: an authed server that is also mutating still has every tool held for the owner's Approval (ADR-0003), so connecting with a credential never lets a mutation through without consent — auth and risk are orthogonal axes. The credential-exists axis mirrors ADR-0009 so the same disconnect-flips-inert guarantee holds, and keeping decryption inside the DO (closest to use, never in the pure `packages/api` domain modules) respects the runtime-adapter boundary of ADR-0006.

The first authenticated servers are user-registered connections (their secret already stored from the MCP registry) and the built-in `context7` via a shared product key; per-user keys for built-in authed servers, and OAuth-based MCP servers, are deferred. Considered alternatives: refusing the grant unless a credential is already resolvable (rejected — it couples grant-time to credential state and diverges from how model-provider and connected-account grants treat the grant and the credential as independent axes); carrying the decrypted credential on the `GrantableMcpServer` shape so the runtime need not re-fetch it (rejected — it would drag a secret through the pure domain modules and the grant catalog, so the DO fetches and decrypts by connection id instead); and giving built-in authed servers a per-user secret store now (deferred — over-built for one server, and a shared product key is enough until a built-in needs per-user scoping). The standing constraint, reinforcing ADR-0006, is that the credential, its Permission, and the credential-exists axis are Better Agent's own product concepts; Think's MCP transport and header plumbing are only the mechanism that carries the injected credential.
